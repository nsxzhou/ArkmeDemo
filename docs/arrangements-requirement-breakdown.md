# 即我「安排」模块需求拆解

## 1. 背景与目标

本需求来自候选人笔试题中的原始口述：基于现有即我移动端 Demo，新增并迭代「安排」模块。

「安排」不是传统待办、日程、任务、提醒的简单合集，而是一个更高层的产品抽象：统一承载那些“还没有发生，但后续需要用户或 AI 推进落地”的事情。它需要从用户主动输入、发给自己、私聊、群聊等场景中识别安排，也要允许用户手动创建，避免 AI 识别失败时阻断用户。

本拆解用于指导后续开发，不直接实现功能。

## 2. 核心产品理解

### 2.1 安排的本质

安排项是用户未来可能需要关注、执行、确认或交给 AI 推进的事项。它可以覆盖：

- 待办：例如“明天买药”。
- 日程：例如“后天下午 3 点去医院”。
- 任务：例如“这周整理面试反馈”。
- 提醒：例如“晚上 8 点提醒我给妈妈打电话”。
- 规划：例如“下个月开始恢复游泳”。

这些不应在首层拆成多个割裂模块，而应统一为「安排项」，再通过时间、提醒、完成方式、来源和执行主体等属性表达差异。

### 2.2 产品哲学

安排模块不能照搬传统效率工具的强约束逻辑。题目中特别强调：

- 人生充满变数，未完成不等于失败。
- 不应让过期事项大面积标红，制造焦虑。
- 真正值得关注的安排是少数。
- 产品应帮助用户整理和推进，而不是不断堆积压力。

因此，安排模块应更像一个温和的未来事项管理器，而不是高压任务清单。

## 3. 功能模块拆解

### 3.1 一级入口

已确认决策：安排作为底部导航一级入口，与「快记」「洞见」「我的」并列。

原因：

- 题目将安排定义为即我的全新核心模块。
- 一级入口能体现模块重要性。
- 用户需要高频查看和处理未来事项。

### 3.2 安排列表

安排列表用于展示当前值得用户关注的安排项。

建议能力：

- 按时间、重要性、最近更新或来源聚合排序。
- 区分今日、近期、以后、无明确时间。
- 显示标题、时间、关联人、地点、来源标识和当前状态。
- 对过期未完成事项采用温和提示，不使用强烈红色压迫式警告。
- 支持右滑或长按操作：完成、以后再说、编辑、查看详情。

### 3.3 手动创建

手动创建是必须能力，因为 AI 无法可靠理解隐喻、暗号或高度私人化表达。

例如用户输入“～～”，其真实含义可能是“游泳”，AI 不应强行猜测。

手动创建至少支持：

- 标题。
- 备注。
- 时间或无时间。
- 地点。
- 关联人。
- 提醒配置。

### 3.4 安排详情

详情页需要展示安排项本身，也要展示上下文来源。

建议包含：

- 安排标题与当前状态。
- 时间、地点、关联人。
- 提醒配置。
- 来源类型：手动、发给自己、私聊、群聊、AI 更新。
- 关联对话上下文列表。
- 合并来源说明。
- 操作区：完成、以后再说、编辑、删除或归档。

### 3.5 完成机制

安排不能无限堆积，必须有完成和沉降机制。

完成方式：

- 用户手动完成。
- AI 根据后续对话推断完成，但应允许用户确认或撤销。

状态建议：

- 待处理。
- 进行中。
- 已完成。
- 以后再说。
- 已沉降。

### 3.6 以后再说

已确认决策：过期未完成事项采用“温和沉降 + 以后再说”机制。

体验目标：

- 用户不想完成，也不想删除，又暂时无法重新规划时间时，可以快速选择“以后再说”。
- 选择后该安排从高关注列表中降噪，但仍可在历史或沉降区找回。
- 不把未完成事项渲染成一大堆红色失败提醒。

### 3.7 日历总览

时间明确的安排需要进入日历视图。

日历不是首版必须完整实现，但蓝图中应保留：

- 月视图或周视图总览。
- 当天安排摘要。
- 日程型安排的时间段展示。
- 截止型安排的日期标记。
- 无明确时间安排不强行塞入日历。

## 4. AI 识别能力拆解

### 4.1 模型接入

已确认决策：首版接入真实 OpenAI 兼容接口。

用户需要可配置：

- `baseUrl`
- `apiKey`
- `model`

配置入口建议放在「我的 > 设置」，而不是安排首页。

注意事项：

- 不在代码中内置 API Key。
- 明确提示用户将消耗自己的 token。
- API 调用失败时保留手动创建，不阻断主流程。

### 4.2 发给自己识别

已确认决策：首个真实 AI 场景优先跑通“发给自己识别安排”。

示例：

```text
后天去一趟医院
```

AI 应提取：

- 标题：去医院。
- 时间：后天。
- 类型倾向：日程或待处理安排。
- 置信度。

交互建议：

- AI 识别后不直接静默创建。
- 先展示待确认卡片。
- 用户确认后进入安排列表。

### 4.3 私聊承诺识别

私聊中需要识别“别人提出请求 + 我答应”的安排。

示例：

```text
对方：明天来公司帮我带个早餐。
我：好的。
```

对自己生成：

```text
明天到公司帮对方带早餐
```

对方侧可理解为：

```text
我明天会来公司帮对方带早餐
```

该能力需要理解：

- 说话人身份。
- 请求对象。
- 用户是否承诺。
- 时间、地点、事项。

### 4.4 群聊识别

已确认决策：群聊默认只展示和自己有关的安排。

原因：

- 安排模块定位为个人未来事项管理。
- 群内全部安排会带来过多噪音。
- 只展示相关事项更符合反焦虑原则。

后续可扩展“查看群内全部安排”的筛选，但不作为默认逻辑。

### 4.5 连续对话识别

题目中特别提到连续对话中的物品累积场景。

示例：

```text
对方：明天帮我带 A。
对方：还有 B。
对方：C 也要。
我：好的。
```

AI 应识别为一条安排：

```text
明天帮对方带 A、B、C
```

而不是创建三条割裂事项。

### 4.6 合并归集

多个来源指向同一事项时，应合并为一个安排项。

示例：

- 用户自己写：“后天去医院。”
- 爸爸提醒：“一定记得去医院。”
- 姐姐询问：“身体情况怎么办？”
- 用户回复：“已经挂号了。”

这些应归集到同一条“去医院检查”安排中，并在详情中展示所有相关上下文。

### 4.7 完成状态推断

AI 可根据后续对话判断安排可能已经完成。

示例：

```text
我今天上午去医院体检了，身体没啥情况。
```

AI 可将之前“去医院检查”的安排标记为可能已完成，并提示用户确认。

## 5. 数据对象建议

### 5.1 ArrangementItem

建议核心字段：

```ts
type ArrangementItem = {
  id: string;
  title: string;
  description?: string;
  status: "pending" | "in_progress" | "completed" | "later" | "settled";
  sourceType: "manual" | "self" | "private_chat" | "group_chat" | "ai_update";
  time?: ArrangementTime;
  location?: string;
  participants: ArrangementParticipant[];
  reminders: ArrangementReminder[];
  contextRefs: ArrangementContextRef[];
  ai?: ArrangementAiMeta;
  createdAt: number;
  updatedAt: number;
};
```

### 5.2 ArrangementTime

```ts
type ArrangementTime = {
  kind: "none" | "deadline" | "time_range" | "fuzzy" | "recurring";
  startAt?: number;
  endAt?: number;
  originalText?: string;
};
```

### 5.3 ArrangementContextRef

```ts
type ArrangementContextRef = {
  sourceType: "self" | "private_chat" | "group_chat";
  conversationId?: string;
  messageId?: string;
  text: string;
  senderName?: string;
  sentAt: number;
};
```

### 5.4 ArrangementAiMeta

```ts
type ArrangementAiMeta = {
  provider: "openai-compatible";
  model: string;
  confidence: number;
  reason?: string;
  needsUserConfirmation: boolean;
};
```

## 6. 版本节奏

### V1：安排基础闭环

目标：证明安排模块的产品理解和交互质感。

范围：

- 底部一级入口“安排”。
- 安排列表。
- 手动创建安排。
- 安排详情。
- 完成安排。
- 以后再说。
- 本地存储。

### V2：真实 AI 接入与发给自己识别

目标：跑通用户自填 API Key 后的真实识别链路。

范围：

- 设置页增加 OpenAI 兼容 API 配置。
- 发给自己内容调用模型识别安排。
- 识别结果确认卡片。
- 失败兜底与手动创建入口。

### V3：私聊识别

目标：识别“请求 + 承诺”的安排。

范围：

- 读取私聊上下文。
- 判断用户是否答应。
- 创建带来源对话的安排。
- 从安排详情跳回原对话。

### V4：合并归集与完成判断

目标：让安排不只是新增，还能持续理解上下文。

范围：

- 相似安排合并。
- 多来源上下文详情。
- AI 推断完成状态。
- 用户确认或撤销 AI 状态变更。

### V5：群聊、日历与提醒

目标：完善复杂协作和时间管理能力。

范围：

- 群聊中只识别与自己有关的安排。
- 连续对话物品累积识别。
- 日历总览。
- 提醒配置。
- 重复提醒。

## 7. 验收场景

### 基础场景

- 用户能从底部导航进入“安排”。
- 用户能手动创建“后天去医院”。
- 用户能查看安排详情。
- 用户能将安排标记为完成。
- 用户能对过期未完成事项选择“以后再说”。

### AI 场景

- 用户配置 OpenAI 兼容 API 后，在发给自己输入“后天去一趟医院”，系统能识别出待确认安排。
- API 失败时，页面给出温和失败提示，并允许用户手动创建。
- 私聊中“明天来公司帮我带个早餐 / 好的”能生成自己的安排。
- 连续私聊消息中的 A、B、C 物品能合并为一条安排。
- 群聊中只展示与自己有关的安排。

### 合并与完成场景

- 多条医院相关消息能归集到同一条安排。
- 详情中能看到每条来源上下文。
- 用户说“今天上午去医院体检了”后，AI 能提示该安排可能已完成。

## 8. 已确认决策与假设

已确认决策：

- 输出目标是指导后续开发。
- 需求拆解采用完整模块蓝图。
- 安排作为底部一级入口。
- 安排项采用统一实体，通过属性表达差异。
- 首版 AI 接入真实 OpenAI 兼容接口。
- 模型配置使用 `baseUrl + apiKey + model`。
- 群聊默认只展示与自己有关的安排。
- 过期未完成采用“温和沉降 + 以后再说”。
- 第一个 AI 场景优先做“发给自己识别”。

当前假设：

- 首阶段不接后端，数据可先保存在本地。
- 不在项目中内置任何 API Key。
- UI 风格沿用现有即我 Demo。
- 本文档只做需求拆解，不代表本轮已经实现功能。
