# 即我「安排」模块需求拆解

## 1. 背景与目标

本需求来自候选人笔试题中的原始口述：基于现有即我移动端 Demo，新增并迭代「安排」模块。

「安排」不是传统待办、日程、任务、提醒的简单合集，而是一个更高层的产品抽象：统一承载那些“还没有发生，但后续需要用户或 AI 推进落地”的事情。它需要从用户主动输入、发给自己、私聊、群聊等场景中识别安排，也要允许用户手动创建，避免 AI 识别失败时阻断用户。

本拆解用于指导后续开发，并在每轮实现后同步标记完成状态。

## 0. 当前实现状态

- V1「安排基础闭环」已完成：底部一级入口、安排列表、手动创建、安排详情、完成、以后再说、本地存储均已落地。
- V1 已额外落地：示例安排、清空/恢复示例、温和过期提示、编辑、重新关注、删除、提醒字段保存与展示。
- V2「真实 AI 接入与发给自己识别」已完成：AI 模型设置、OpenAI 兼容接口调用、发给自己自动识别、直接创建安排、识别状态提示、失败兜底和本地幂等均已落地。
- V3「私聊承诺识别」已完成：用户在私聊中回复后，系统可读取最近上下文、判断“请求 + 承诺”、高置信直接创建私聊来源安排，并支持从安排详情回跳原私聊。
- V4「合并归集与完成判断」已完成：发给自己和私聊来源创建新安排后，可检测相似安排并在详情中提示用户确认合并；后续明确完成消息可在高置信时自动标记完成，并保留 AI 依据和撤销入口。
- V5「群聊、日历与应用内提醒」已完成：群聊回复后可识别与自己有关的安排，支持连续对话物品累积；安排页已增加清单/日历切换、月视图总览、当天安排列表和应用内提醒提示。
- V6「轻整理与提醒降噪」已完成：安排页顶部增加今日轻整理面板，支持提醒已知晓、明早稍后提醒、过期 7 天以上安排手动沉降、最近沉降项恢复；新安排创建后可触发每小时最多一次的 AI 自动沉降扫描，并保留沉降依据和原状态恢复入口。
- 当前实现不接后端、不内置 API Key、不触发系统通知。

## 2. 核心产品理解

### 2.1 安排的本质

安排项是用户未来可能需要关注、执行、确认或交给 AI 推进的事项。它可以覆盖：

- 待办：例如“明天买药”。
- 日程：例如“后天下午 3 点去医院”。
- 任务：例如“这周整理面试反馈”。
- 提醒：例如“晚上 8 点提醒我给妈妈打电话”。
- 规划：例如“下个月开始恢复游泳”。

这些不应在首层拆成多个割裂模块，而应统一为「安排项」，再通过时间、提醒、完成方式、来源和执行主体等属性表达差异。

### 2.2 产品哲学

安排模块不能照搬传统效率工具的强约束逻辑。题目中特别强调：

- 人生充满变数，未完成不等于失败。
- 不应让过期事项大面积标红，制造焦虑。
- 真正值得关注的安排是少数。
- 产品应帮助用户整理和推进，而不是不断堆积压力。

因此，安排模块应更像一个温和的未来事项管理器，而不是高压任务清单。

## 3. 功能模块拆解

### 3.1 一级入口

状态：已完成。

已确认决策：安排作为底部导航一级入口，与「快记」「洞见」「我的」并列。

原因：

- 题目将安排定义为即我的全新核心模块。
- 一级入口能体现模块重要性。
- 用户需要高频查看和处理未来事项。

### 3.2 安排列表

状态：已完成。

安排列表用于展示当前值得用户关注的安排项。

建议能力：

- 按时间、重要性、最近更新或来源聚合排序。
- 区分今日、近期、以后、无明确时间。
- 显示标题、时间、关联人、地点、来源标识和当前状态。
- 对过期未完成事项采用温和提示，不使用强烈红色压迫式警告。
- 支持右滑或长按操作：完成、以后再说、编辑、查看详情。

实现说明：

- V1 已实现按今日、近期、无明确时间、以后再说分组展示。
- V1 已展示标题、时间、关联人、地点和当前状态。
- V1 已对过期未完成事项使用温和提示，不使用强烈红色警告。
- V1 的操作入口目前在详情弹层中提供，右滑或长按可作为后续交互增强。

### 3.3 手动创建

状态：已完成。

手动创建是必须能力，因为 AI 无法可靠理解隐喻、暗号或高度私人化表达。

例如用户输入“～～”，其真实含义可能是“游泳”，AI 不应强行猜测。

手动创建至少支持：

- 标题。
- 备注。
- 时间或无时间。
- 地点。
- 关联人。
- 提醒配置。

### 3.4 安排详情

状态：已完成基础能力。

详情页需要展示安排项本身，也要展示上下文来源。

建议包含：

- 安排标题与当前状态。
- 时间、地点、关联人。
- 提醒配置。
- 来源类型：手动、发给自己、私聊、群聊、AI 更新。
- 关联对话上下文列表。
- 合并来源说明。
- 操作区：完成、以后再说、编辑、删除或归档。

实现说明：

- V1 已展示标题、状态、时间、地点、关联人、提醒、来源和来源上下文。
- V1 已支持完成、以后再说、重新关注、编辑、删除。
- V3 已支持私聊来源上下文列表展示，并可从详情跳回原私聊定位来源消息。
- V4 已支持发给自己和私聊来源的相似安排合并建议，用户确认后可在同一条安排详情中查看多来源上下文。
- V6 已支持沉降线索展示：AI 或轻整理将安排沉降后，详情中展示置信度、原因和恢复入口，恢复时回到沉降前状态。

### 3.5 完成机制

状态：部分完成。

安排不能无限堆积，必须有完成和沉降机制。

完成方式：

- 用户手动完成。（已完成）
- AI 根据后续对话推断完成，并允许用户撤销。（已完成，V4 采用高置信自动完成 + 详情撤销入口）

状态建议：

- 待处理。
- 进行中。
- 已完成。
- 以后再说。
- 已沉降。

### 3.6 以后再说

状态：已完成。

已确认决策：过期未完成事项采用“温和沉降 + 以后再说”机制。

体验目标：

- 用户不想完成，也不想删除，又暂时无法重新规划时间时，可以快速选择“以后再说”。
- 选择后该安排从高关注列表中降噪，但仍可在历史或沉降区找回。
- 不把未完成事项渲染成一大堆红色失败提醒。

### 3.7 日历总览

状态：已完成。

时间明确的安排需要进入日历视图。

日历不是首版必须完整实现，但蓝图中应保留：

- 月视图或周视图总览。
- 当天安排摘要。
- 日程型安排的时间段展示。
- 截止型安排的日期标记。
- 无明确时间安排不强行塞入日历。

实现说明：

- V5 已在安排页新增“清单 / 日历”切换，默认仍保持清单视图。
- V5 日历采用月视图 + 选中日期安排列表，只展示 `time.startAt` 明确的安排。
- 无明确时间安排仍保留在清单分组，不强行进入日历。

## 4. AI 识别能力拆解

### 4.1 模型接入

状态：已完成。

已确认决策：首版接入真实 OpenAI 兼容接口。

用户需要可配置：

- `baseUrl`
- `apiKey`
- `model`

配置入口建议放在「我的 > 设置」，而不是安排首页。

注意事项：

- 不在代码中内置 API Key。
- 明确提示用户将消耗自己的 token。
- API 调用失败时保留手动创建，不阻断主流程。

实现说明：

- V2 已在「我的 > 设置 > AI 模型设置」中落地 `baseUrl + apiKey + model` 配置。
- 源码只预置测试 `baseUrl` 和 `model`，API Key 由用户本机输入并仅保存到 `localStorage`。
- V2 使用 OpenAI 兼容 `chat/completions` JSON 输出识别安排。

### 4.2 发给自己识别

状态：已完成。

已确认决策：首个真实 AI 场景优先跑通“发给自己识别安排”。

示例：

```text
后天去一趟医院
```

AI 应提取：

- 标题：去医院。
- 时间：后天。
- 类型倾向：日程或待处理安排。
- 置信度。

实现说明：

- V2 已按最新确认改为“自动识别 + 直接创建”：发给自己发送新内容后自动调用模型，命中安排时直接创建安排项。
- 创建结果在发给自己聊天内显示轻提示，可点击进入安排详情。
- 同一条发给自己的消息通过 `recordUid` 幂等，只创建一次安排。
- 未配置 API Key 或 API/CORS/解析失败时，保留快记并显示可重试失败状态。

### 4.3 私聊承诺识别

状态：已完成。

私聊中需要识别“别人提出请求 + 我答应”的安排。

示例：

```text
对方：明天来公司帮我带个早餐。
我：好的。
```

对自己生成：

```text
明天到公司帮对方带早餐
```

对方侧可理解为：

```text
我明天会来公司帮对方带早餐
```

该能力需要理解：

- 说话人身份。
- 请求对象。
- 用户是否承诺。
- 时间、地点、事项。

实现说明：

- V3 已在移动端私聊回复后触发识别，不在收到对方消息时提前创建。
- V3 复用现有 OpenAI 兼容模型设置，并新增“自动识别私聊回复”开关。
- V3 使用最近 8 条私聊上下文判断是否存在“请求 + 承诺”。
- V3 仅在 `confidence >= 0.72` 且用户明确承诺时直接创建 `sourceType=private_chat` 的安排。
- V3 按 `conversationId + replyMessageId` 幂等，同一条回复不重复识别或重复创建。
- V3 对无安排、低置信和非承诺回复保持低干扰，不展示噪音提示；缺配置或失败时显示可重试提示。

### 4.4 群聊识别

状态：已完成。

已确认决策：群聊默认只展示和自己有关的安排。

原因：

- 安排模块定位为个人未来事项管理。
- 群内全部安排会带来过多噪音。
- 只展示相关事项更符合反焦虑原则。

后续可扩展“查看群内全部安排”的筛选，但不作为默认逻辑。

实现说明：

- V5 已在移动端群聊中接入“我方回复后触发”的群聊识别链路。
- V5 读取同群最近 12 条消息，要求模型返回 `hasArrangement=true`、`isUserCommitted=true`、`isRelatedToMe=true` 且 `confidence >= 0.8` 后才创建 `sourceType=group_chat` 安排。
- V5 按 `conversationId + replyMessageId` 做本地幂等，缺 API Key 或识别失败时只显示低干扰提示和重试入口。
- V5 支持从群聊来源安排详情回跳到原群聊消息。

### 4.5 连续对话识别

状态：已完成。

题目中特别提到连续对话中的物品累积场景。

示例：

```text
对方：明天帮我带 A。
对方：还有 B。
对方：C 也要。
我：好的。
```

AI 应识别为一条安排：

```text
明天帮对方带 A、B、C
```

而不是创建三条割裂事项。

实现说明：

- V5 群聊识别提示词要求模型把连续补充的 A、B、C 等物品合并为一条安排。
- 该能力随群聊回复识别一起落地，不为连续补充消息分别创建多条安排。

### 4.6 合并归集

状态：已完成。

多个来源指向同一事项时，应合并为一个安排项。

示例：

- 用户自己写：“后天去医院。”
- 爸爸提醒：“一定记得去医院。”
- 姐姐询问：“身体情况怎么办？”
- 用户回复：“已经挂号了。”

这些应归集到同一条“去医院检查”安排中，并在详情中展示所有相关上下文。

实现说明：

- V4 已在发给自己和私聊识别创建新安排后，调用 OpenAI 兼容模型判断是否与现有关注中安排相似。
- 相似安排不会自动合并，而是在新安排详情中展示“可能相关安排”提示。
- 用户确认合并后，保留较早创建的安排作为主安排，合入新来源上下文、参与人、提醒和 AI 信息，并移除被合并安排。
- V5 已将群聊来源新安排接入 V4 相似安排检测，群聊来源也可在详情中提示用户确认合并。

### 4.7 完成状态推断

状态：已完成。

AI 可根据后续对话判断安排可能已经完成。

示例：

```text
我今天上午去医院体检了，身体没啥情况。
```

AI 可将之前“去医院检查”的安排标记为可能已完成，并提示用户确认。

实现说明：

- V4 已在发给自己和私聊新消息后，对当前关注中的安排执行完成状态推断。
- V5 已将群聊回复接入同一完成状态推断链路。
- 只有模型明确判断已完成且 `confidence >= 0.9` 时，才自动标记为已完成。
- 自动完成会在安排详情中保留 AI 状态线索、来源消息、置信度和撤销入口。
- 缺 API Key、请求失败、解析失败、低置信或模糊表达不会改变安排状态。

### 4.8 轻整理与沉降

状态：已完成。

当安排逐渐堆积时，系统需要帮助用户降噪，但不能把“未完成”包装成失败。

实现说明：

- V6 已在安排页顶部新增“今日轻整理”面板，集中展示需要留意的提醒、过期 7 天以上的降噪建议和最近已沉降项。
- 对已到期或 24 小时内的提醒，用户可以选择“已知晓”或“明早提醒”；已知晓会记录到提醒上，刷新后不再重复展示，稍后提醒会把提醒时间推到本地明天 9:00。
- 对过期 7 天以上、仍处于关注中的安排，用户可以在轻整理面板中手动沉降。
- 新安排创建后，系统可调用 OpenAI 兼容模型进行全量轻整理扫描；扫描每小时最多一次，模型可参考所有本地安排，并在 `confidence >= 0.9` 时自动沉降安排。
- 自动沉降会保存 `settlementEvidence.previousStatus`、模型、置信度、原因、触发安排 ID 和沉降时间；用户可从详情或轻整理面板恢复到原状态。

## 8. 已确认决策与假设

已确认决策：

- 输出目标是指导后续开发。
- 需求拆解采用完整模块蓝图。
- 安排作为底部一级入口。

- 首版 AI 接入真实 OpenAI 兼容接口。
- 模型配置使用 `baseUrl + apiKey + model`。
- 群聊默认只展示与自己有关的安排。
- 过期未完成采用“温和沉降 + 以后再说”。
- 第一个 AI 场景优先做“发给自己识别”。
- 新安排创建后允许触发 AI 轻整理扫描，但通过 `arkme-demo.arrangementContinuity.settlementRun` 做每小时最多一次的本地节流。

- 首阶段不接后端，数据可先保存在本地。（已按 V1 实现）
- 不在项目中内置任何 API Key。
- UI 风格沿用现有即我 Demo。
- 本文档持续作为需求拆解和进度标记来源；V1-V6 已实现，重复提醒和后端同步仍未实现。
