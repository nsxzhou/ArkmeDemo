# 即我「安排」模块需求拆解

## 1. 背景与目标

本需求来自候选人笔试题中的原始口述：基于现有即我移动端 Demo，新增并迭代「安排」模块。

「安排」不是传统待办、日程、任务、提醒的简单合集，而是一个更高层的产品抽象：统一承载那些“还没有发生，但后续需要用户或 AI 推进落地”的事情。它需要从用户主动输入、发给自己、私聊、群聊等场景中识别安排，也要允许用户手动创建，避免 AI 识别失败时阻断用户。

本拆解用于指导后续开发，并在每轮实现后同步标记完成状态。

## 0. 当前实现状态

- V1「安排基础闭环」已完成：底部一级入口、安排列表、手动创建、安排详情、完成、以后再说、本地存储均已落地。
- V1 已额外落地：示例安排、清空/恢复示例、温和过期提示、编辑、重新关注、删除、提醒字段保存与展示。
- V2「真实 AI 接入与发给自己识别」已完成：AI 模型设置、OpenAI 兼容接口调用、发给自己自动识别、直接创建安排、识别状态提示、失败兜底和本地幂等均已落地。
- V3「私聊承诺识别」已完成：用户在私聊中回复后，系统可读取最近上下文、判断“请求 + 承诺”、高置信直接创建私聊来源安排，并支持从安排详情回跳原私聊。
- V4-V5 尚未实现：群聊识别、合并归集、AI 完成判断、日历总览、真实提醒通知仍为后续规划。
- 当前实现不接后端、不内置 API Key、不触发系统通知。

## 2. 核心产品理解

### 2.1 安排的本质

安排项是用户未来可能需要关注、执行、确认或交给 AI 推进的事项。它可以覆盖：

- 待办：例如“明天买药”。
- 日程：例如“后天下午 3 点去医院”。
- 任务：例如“这周整理面试反馈”。
- 提醒：例如“晚上 8 点提醒我给妈妈打电话”。
- 规划：例如“下个月开始恢复游泳”。

这些不应在首层拆成多个割裂模块，而应统一为「安排项」，再通过时间、提醒、完成方式、来源和执行主体等属性表达差异。

### 2.2 产品哲学

安排模块不能照搬传统效率工具的强约束逻辑。题目中特别强调：

- 人生充满变数，未完成不等于失败。
- 不应让过期事项大面积标红，制造焦虑。
- 真正值得关注的安排是少数。
- 产品应帮助用户整理和推进，而不是不断堆积压力。

因此，安排模块应更像一个温和的未来事项管理器，而不是高压任务清单。

## 3. 功能模块拆解

### 3.1 一级入口

状态：已完成。

已确认决策：安排作为底部导航一级入口，与「快记」「洞见」「我的」并列。

原因：

- 题目将安排定义为即我的全新核心模块。
- 一级入口能体现模块重要性。
- 用户需要高频查看和处理未来事项。

### 3.2 安排列表

状态：已完成。

安排列表用于展示当前值得用户关注的安排项。

建议能力：

- 按时间、重要性、最近更新或来源聚合排序。
- 区分今日、近期、以后、无明确时间。
- 显示标题、时间、关联人、地点、来源标识和当前状态。
- 对过期未完成事项采用温和提示，不使用强烈红色压迫式警告。
- 支持右滑或长按操作：完成、以后再说、编辑、查看详情。

实现说明：

- V1 已实现按今日、近期、无明确时间、以后再说分组展示。
- V1 已展示标题、时间、关联人、地点和当前状态。
- V1 已对过期未完成事项使用温和提示，不使用强烈红色警告。
- V1 的操作入口目前在详情弹层中提供，右滑或长按可作为后续交互增强。

### 3.3 手动创建

状态：已完成。

手动创建是必须能力，因为 AI 无法可靠理解隐喻、暗号或高度私人化表达。

例如用户输入“～～”，其真实含义可能是“游泳”，AI 不应强行猜测。

手动创建至少支持：

- 标题。
- 备注。
- 时间或无时间。
- 地点。
- 关联人。
- 提醒配置。

### 3.4 安排详情

状态：已完成基础能力。

详情页需要展示安排项本身，也要展示上下文来源。

建议包含：

- 安排标题与当前状态。
- 时间、地点、关联人。
- 提醒配置。
- 来源类型：手动、发给自己、私聊、群聊、AI 更新。
- 关联对话上下文列表。
- 合并来源说明。
- 操作区：完成、以后再说、编辑、删除或归档。

实现说明：

- V1 已展示标题、状态、时间、地点、关联人、提醒、来源和来源上下文。
- V1 已支持完成、以后再说、重新关注、编辑、删除。
- V3 已支持私聊来源上下文列表展示，并可从详情跳回原私聊定位来源消息。
- 多来源合并说明依赖 V4 合并归集能力，尚未实现。

### 3.5 完成机制

状态：部分完成。

安排不能无限堆积，必须有完成和沉降机制。

完成方式：

- 用户手动完成。（已完成）
- AI 根据后续对话推断完成，但应允许用户确认或撤销。（未实现，规划在 V4）

状态建议：

- 待处理。
- 进行中。
- 已完成。
- 以后再说。
- 已沉降。

### 3.6 以后再说

状态：已完成。

已确认决策：过期未完成事项采用“温和沉降 + 以后再说”机制。

体验目标：

- 用户不想完成，也不想删除，又暂时无法重新规划时间时，可以快速选择“以后再说”。
- 选择后该安排从高关注列表中降噪，但仍可在历史或沉降区找回。
- 不把未完成事项渲染成一大堆红色失败提醒。

### 3.7 日历总览

状态：未实现，保留在 V5。

时间明确的安排需要进入日历视图。

日历不是首版必须完整实现，但蓝图中应保留：

- 月视图或周视图总览。
- 当天安排摘要。
- 日程型安排的时间段展示。
- 截止型安排的日期标记。
- 无明确时间安排不强行塞入日历。

## 4. AI 识别能力拆解

### 4.1 模型接入

状态：已完成。

已确认决策：首版接入真实 OpenAI 兼容接口。

用户需要可配置：

- `baseUrl`
- `apiKey`
- `model`

配置入口建议放在「我的 > 设置」，而不是安排首页。

注意事项：

- 不在代码中内置 API Key。
- 明确提示用户将消耗自己的 token。
- API 调用失败时保留手动创建，不阻断主流程。

实现说明：

- V2 已在「我的 > 设置 > AI 模型设置」中落地 `baseUrl + apiKey + model` 配置。
- 源码只预置测试 `baseUrl` 和 `model`，API Key 由用户本机输入并仅保存到 `localStorage`。
- V2 使用 OpenAI 兼容 `chat/completions` JSON 输出识别安排。

### 4.2 发给自己识别

状态：已完成。

已确认决策：首个真实 AI 场景优先跑通“发给自己识别安排”。

示例：

```text
后天去一趟医院
```

AI 应提取：

- 标题：去医院。
- 时间：后天。
- 类型倾向：日程或待处理安排。
- 置信度。

实现说明：

- V2 已按最新确认改为“自动识别 + 直接创建”：发给自己发送新内容后自动调用模型，命中安排时直接创建安排项。
- 创建结果在发给自己聊天内显示轻提示，可点击进入安排详情。
- 同一条发给自己的消息通过 `recordUid` 幂等，只创建一次安排。
- 未配置 API Key 或 API/CORS/解析失败时，保留快记并显示可重试失败状态。

### 4.3 私聊承诺识别

状态：已完成。

私聊中需要识别“别人提出请求 + 我答应”的安排。

示例：

```text
对方：明天来公司帮我带个早餐。
我：好的。
```

对自己生成：

```text
明天到公司帮对方带早餐
```

对方侧可理解为：

```text
我明天会来公司帮对方带早餐
```

该能力需要理解：

- 说话人身份。
- 请求对象。
- 用户是否承诺。
- 时间、地点、事项。

实现说明：

- V3 已在移动端私聊回复后触发识别，不在收到对方消息时提前创建。
- V3 复用现有 OpenAI 兼容模型设置，并新增“自动识别私聊回复”开关。
- V3 使用最近 8 条私聊上下文判断是否存在“请求 + 承诺”。
- V3 仅在 `confidence >= 0.72` 且用户明确承诺时直接创建 `sourceType=private_chat` 的安排。
- V3 按 `conversationId + replyMessageId` 幂等，同一条回复不重复识别或重复创建。
- V3 对无安排、低置信和非承诺回复保持低干扰，不展示噪音提示；缺配置或失败时显示可重试提示。

### 4.4 群聊识别

状态：未实现，规划在 V5。

已确认决策：群聊默认只展示和自己有关的安排。

原因：

- 安排模块定位为个人未来事项管理。
- 群内全部安排会带来过多噪音。
- 只展示相关事项更符合反焦虑原则。

后续可扩展“查看群内全部安排”的筛选，但不作为默认逻辑。

### 4.5 连续对话识别

状态：未实现，规划在 V5。

题目中特别提到连续对话中的物品累积场景。

示例：

```text
对方：明天帮我带 A。
对方：还有 B。
对方：C 也要。
我：好的。
```

AI 应识别为一条安排：

```text
明天帮对方带 A、B、C
```

而不是创建三条割裂事项。

### 4.6 合并归集

状态：未实现，规划在 V4。

多个来源指向同一事项时，应合并为一个安排项。

示例：

- 用户自己写：“后天去医院。”
- 爸爸提醒：“一定记得去医院。”
- 姐姐询问：“身体情况怎么办？”
- 用户回复：“已经挂号了。”

这些应归集到同一条“去医院检查”安排中，并在详情中展示所有相关上下文。

### 4.7 完成状态推断

状态：未实现，规划在 V4。

AI 可根据后续对话判断安排可能已经完成。

示例：

```text
我今天上午去医院体检了，身体没啥情况。
```

AI 可将之前“去医院检查”的安排标记为可能已完成，并提示用户确认。

## 5. 数据对象建议

### 5.1 ArrangementItem

状态：已完成基础类型定义。

建议核心字段：

```ts
type ArrangementItem = {
  id: string;
  title: string;
  description?: string;
  status: "pending" | "in_progress" | "completed" | "later" | "settled";
  sourceType: "manual" | "self" | "private_chat" | "group_chat" | "ai_update";

  location?: string;
  participants: ArrangementParticipant[];

  createdAt: number;
  updatedAt: number;
};
```

实现说明：V1 已在 `src/types/arrangement.ts` 中落地 `ArrangementItem`，并增加 `isDemo` 用于区分示例安排。

### 5.2 ArrangementTime

状态：已完成基础类型定义。

```ts
type ArrangementTime = {
  kind: "none" | "deadline" | "time_range" | "fuzzy" | "recurring";
  startAt?: number;
  endAt?: number;
  originalText?: string;
};
```

实现说明：V1 已在 `src/types/arrangement.ts` 中落地 `ArrangementTime`，并支持 `none`、`deadline`、`time_range`、`fuzzy`、`recurring`。

### 5.3 ArrangementContextRef

状态：已完成基础类型定义。

```ts

  sourceType: "self" | "private_chat" | "group_chat";

  senderName?: string;
  sentAt: number;
};
```

实现说明：V1 已支持手动创建和示例来源上下文展示；真实私聊、群聊上下文回跳依赖 V3/V5。

### 5.4 ArrangementAiMeta

状态：已完成类型预留，AI 流程未实现。


## 8. 已确认决策与假设

已确认决策：

- 输出目标是指导后续开发。
- 需求拆解采用完整模块蓝图。
- 安排作为底部一级入口。
- 安排项采用统一实体，通过属性表达差异。
- 首版 AI 接入真实 OpenAI 兼容接口。
- 模型配置使用 `baseUrl + apiKey + model`。
- 群聊默认只展示与自己有关的安排。
- 过期未完成采用“温和沉降 + 以后再说”。
- 第一个 AI 场景优先做“发给自己识别”。

当前假设：

- 首阶段不接后端，数据可先保存在本地。（已按 V1 实现）
- 不在项目中内置任何 API Key。
- UI 风格沿用现有即我 Demo。
- 本文档持续作为需求拆解和进度标记来源；V1 已实现，后续阶段仍未实现。
